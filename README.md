# 对话 Token 用量（token-meter）

> 给 AstrBot 用的小插件。它只干两件事：**让你看见上下文有多大**，**快到线时提醒你一声**。

版本：v1.3.0

---

## 它为什么存在

AstrBot 有上下文压缩，但有个问题：**压缩之前，你看不见。**

你只知道"它好像会自己压"，不知道现在用了多少、离那条线还有多远。等到发现时，往往已经压过了，细节也薄了一层。

这个插件把那个看不见的东西摊开：

```
对话 Token 用量

已用  19.0 万 / 62.9 万
占比  30.2%
[██████░░░░░░░░░░░░░░]

消息  305 条（你 90 / 我 152 / 工具 63）
你的话占  6.4 万
其中思考  3.6 万
上次请求实测  22.4 万 输入（deepseek-flash）
```

再加上一条：**到阈值时，在回复末尾自动附一句提醒。**

---

## 两条功能

### 一、查

```
/查询token
```

（英文别名 `/token`，功能相同）

### 二、到线提醒

每回复一次，它在发送前看一眼用量。超过阈值（默认 95%）就在那条回复末尾附一句：

```
上下文用量到 95.0% 了，还剩 3.1 万 token，到 100% 会自动压缩
```

**带冷却**：提醒过一次之后，要再涨 `remind_cooldown` 个 token 才会再提。不然每句话都念一遍，会很烦。

**只在私聊**：默认不在群聊里报这种数字。

## 安装

1. 把整个文件夹放到：

   ```
   <你的 AstrBot 实例目录>/core/data/plugins/astrbot_plugin_token_meter/
   ```

2. 在面板的插件管理里重载插件（或重启实例）。
3. 面板里找到本插件，把 `max_tokens` 填成你的压缩线（见下面「上限填多少」）。

不需要额外依赖，只用标准库。

---

## 上限填多少 —— 这一节最要紧

`max_tokens` **不是模型窗口**，它只是算百分比的分母。

想让百分比等于「离压缩还有多远」，就填**压缩线**：

```
压缩线 = 模型上下文窗口 × 0.82
```

那个 `0.82` 是 AstrBot 里写死的触发比例（`compressor.py` 里 `compression_threshold` 的默认值），面板上不暴露。

举个例子：

```
DeepSeek flash 的上下文窗口   = 1,048,576
AstrBot 的触发比例            = 0.82
于是压缩线                    = 859,832
```

那你就把 `max_tokens` 填 `859832`。看到 95% 就是真的快压了。

**如果填成 100 万（窗口大小）**，也没错，只是百分比的含义变成"占窗口多少"，到 82% 才会压——那时候看到 80% 还以为是安全的，其实已经很近了。

> 也可以在 provider 配置里手动填 `max_context_tokens` 来改变压缩线本身。
> 那是个**分母**：填小了，压缩来得早、每次压得少；填大了，压缩来得晚、一次压得重。
> 后者风险高——一次性把很大的上下文交给模型做总结，容易失败，失败后会退回"按轮数直接砍"，那是硬丢。

## 配置项

| 配置项 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `max_tokens` | int | `1000000` | 算百分比的分母。建议填压缩线 |
| `show_bar` | bool | `true` | 显示进度条 |
| `show_detail` | bool | `true` | 显示明细（消息条数、真实用量） |
| `count_think` | bool | `true` | 思考内容算不算进 token |
| `warn_percent` | float | `80.0` | 查询时超过这个百分比加一句 |
| `remind_enable` | bool | `true` | 到线自动提醒总开关 |
| `remind_percent` | float | `95.0` | 自动提醒的阈值 |
| `remind_cooldown` | int | `5000` | 提醒冷却（涨多少 token 才会再提） |
| `remind_private_only` | bool | `true` | 只在私聊提醒 |
| `remind_target` | string | 空 | 只对指定会话提醒，留空＝所有私聊 |
| `verbose` | bool | `false` | 往日志里打细节 |

## 它是怎么算的

### 估算（查询用）

照 AstrBot 内部 `EstimateTokenCounter` 的规则，逐条消息累加：

| 内容 | 算法 |
| --- | --- |
| 中文 | 0.6 token / 字 |
| 其它字符（英文、数字、标点） | 0.3 token / 字 |
| emoji | 2.0 token / 个 |
| 图片 | 765 token / 张 |
| 音频 | 500 token / 段 |
| 工具调用 | 参数 JSON 当文字算 |

**图片为什么不按字符算**：图片在库里是 base64，一张截图能有 40 万字符。按字符算会得出"这个对话有几十亿 token"这种荒唐结果。模型看一张图只花几百 token，所以按张算。

### 真实值（参照显示）

`provider_stats` 表里记着每次 API 调用实际返回的用量：

```
token_input_other + token_input_cached = 那次请求的真实输入
```

它比估算多出来的是：人格提示词、工具定义、系统消息——那些不在 `conversations` 里，但每次都要发出去。

所以两个数都会显示：

- **已用**（估算）＝ 库里看到的部分
- **上次请求实测**（真实）＝ 实际发出去的总量

两者差 10% 到 20% 是正常的。

## 踩过的坑（v1.2 修的那个）

v1.1 有个 bug：查询和提醒各算各的。

- 查询走估算
- 提醒读 `provider_stats`

结果有一天，查询显示 **30.2%**，提醒却弹出来说 **308.0%**。

原因是 `provider_stats` 里混着脏数据：有一条记录的 `cached` 字段写着 `1,933,952`（比模型窗口还大，明显不对）。提醒把那一条当真了。

v1.2 改了两处：

1. **同一个口径**：查询和提醒都走 `_scan_session()`，一次扫描出总数、条数、角色分布。两个数字永远一致。
2. **合理性筛**：真实值超过 `max_tokens × 2` 的，视为脏数据，不参与判断。

顺带把提醒从多行改成单行——多行会被平台的自动分段拆成好几个气泡，看着像刷屏。

**给别人的提醒**：如果你要读 `provider_stats`，记得先做一遍合理性检查。那张表里的数据不总是干净的。

## 已知限制

- **扫描是每次全量算。** 消息多的时候（比如 300 条以上），一次要几百毫秒。库特别大时会更久。这是为了数字准确故意没做缓存的。
- **估算永远不等于真实值。** 差的那部分是提示词和工具定义，估算看不见。
- **`max_context_tokens` 会被 AstrBot 的模型元数据覆盖。** 如果 provider 里没手动填，AstrBot 会去 models.dev 查，查不到才用 `fallback_max_tokens`。所以你很可能根本没用到那个兜底值——先确认清楚再调。
- **只读**：这个插件从头到尾只读数据库（`mode=ro`，失败退 `immutable=1`），不写任何文件、不改任何配置。
